# Selector capture bound to an authenticated human

`EvidenceService.captureSelectorLinksForHuman(request, selectors, humanId)` is an additive explicit opt-in to the existing owning capture. The expected ID must be a nonempty string of at most128 characters before credential resolution. Actual credential-directory authentication must yield a human with that exact ID before SQL starts, and again after the owning project lock/current directory reload. A service or agent with the same textual ID cannot satisfy this profile. The same current source scope, purpose, clean-scan, selector/family fingerprints, full response bounds and private metadata projection apply.

The expected ID is a comparison target, not authentication. A protected caller must obtain it from its independently authenticated current human context; caller flags, diagnostic strings or snapshots do not establish that identity. The service authenticates the credential against the trusted Evidence directory. Directory proofing, unique cross-engine ID mapping, session/login identity, delegated credential release, credential custody and current Identity/Consent decisions remain host/consumer responsibilities. A configured service/delegated principal is intentionally insufficient for this human-only profile. Existing two-argument capture/review APIs retain their own documented trust boundaries; rejection here never falls back to them. Consumers must explicitly upgrade the SDK pin and choose the human-bound method. Existing Knowledge paths have not adopted it by this change.

Only the existing checked-read capture audit is committed, with its actual authenticated actor and selector count. No expected-ID authority, token, grant, domain revision, business outbox/effect, object read/write or response cache is persisted. Denial after the lock rolls back that checked audit. Lost read COMMIT acknowledgement is unknown; an audit may already be committed. A fresh call reloads current identity/source state and can deny. Returned metadata is historical after return, never a current permission/future permit or distributed revocation fence.

This adds no network endpoint, human proofing/login, Consent/rights evaluation, new SQL/migration, byte/scanner qualification, delegation/impersonation authority, provider send/publication/payment or PAM behavior. Host callback deadlines/SQL/CPU/heap/process isolation remain required; this API cannot preempt noncooperative callbacks or SQL. Embedded PGlite is not independent network-session contention, production TLS or deployment qualification.
